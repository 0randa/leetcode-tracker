# Sign in with Google & GitHub — Design

_Date: 2026-06-02. Supersedes the planning sketch in `AUTH-HANDOFF.md` where they
differ (deltas are called out inline). Turns the placeholder sign-in screen into
real, backend-owned OAuth with a real per-user identity threaded end to end._

## Goal

Make **Continue with Google** and **Continue with GitHub** real authentication.
After this work, signing in creates/looks up a real user, issues a server-side
session, and every backend read/write is scoped to the authenticated user instead
of the implicit single user (`user_id = 1`).

## Confirmed decisions

1. **OAuth owner: the backend (Spring).** Both web and the existing iOS client can
   reuse one auth system. Matches CLAUDE.md ("backend owns all logic"; "only the
   backend talks to external services") and the README's stated direction.
2. **Sessions: opaque token + `sessions` table.** httpOnly cookie for web; the same
   token works as a bearer token for iOS later. Trivially revocable.
3. **Guest path: dropped.** The "Continue as guest" button and action are removed.
   Google/GitHub only.
4. **Existing data: start fresh.** The first real login does **not** claim the
   `user_id = 1` data; that data is left in place, unowned.
5. **OAuth implementation: hand-rolled** on the existing `RestClient` idiom (no
   Spring Security). We mint our own opaque session.
6. **Logout UI:** the reserved gear slot in `ProgressStrip` (Today screen) becomes a
   temporary "Sign out" action. No Settings screen is built.

## Deltas from `AUTH-HANDOFF.md`

- **Cookie topology (handoff §3).** The handoff has the provider redirect to the
  *backend*, which sets the session cookie and redirects to web. That requires web
  and backend to share a cookie domain — false in prod (Vercel vs Render are
  separate registrable domains) and in dev (`:5173` vs `:8080` are separate cookie
  scopes), and the browser is only ever supposed to talk to SvelteKit. **Instead:**
  the cookie lives on the **web origin** and SvelteKit relays the handshake to the
  backend server-to-server (the "BFF relay" below).
- **Start-fresh id gap (handoff §2.5).** The handoff defaults to *claiming*
  `user_id = 1`. We chose start-fresh, so `users.id` identity **starts at 1000** to
  guarantee a new login can never land on the orphaned `user_id = 1` rows.
- **No PKCE.** We are a confidential client (client secret on the backend). Signed
  `state` + a BFF-held `oauth_state` cookie is the CSRF defense. PKCE is a small
  future add (it needs a verifier stashed between start and callback) and buys
  little for a confidential server-side client; GitHub OAuth Apps don't support it.

## Architecture — backend-owned OAuth via a BFF relay

The browser only ever talks to SvelteKit. SvelteKit relays the OAuth handshake to
Spring server-to-server; the backend holds all secrets and does the token exchange.

```
Browser ──"Continue with Google"──▶ SvelteKit  POST /signin?/google
SvelteKit ──(server→server)──▶ Spring  GET /auth/google/start   → { authorizeUrl, state }
SvelteKit  sets httpOnly oauth_state cookie · 303 ▶ Google consent
Google ──redirect──▶ SvelteKit  GET /auth/google/callback?code&state   (redirect_uri = web origin)
SvelteKit  verifies state == oauth_state cookie · clears it
SvelteKit ──(server→server)──▶ Spring  POST /auth/google/callback { code, state }
Spring  re-verify state (HMAC+exp+provider) · exchange code (client secret)
        · fetch profile · resolve/create user · create session row → { token, expiresAt, isNewUser }
SvelteKit  Set-Cookie: session=<token> (httpOnly) · 303 ▶ /onboarding (new) or / (returning)

Every later request:
Browser ──▶ SvelteKit  →  hooks.server.ts reads session cookie, validates via GET /auth/me
SvelteKit ──▶ Spring  with  Authorization: Bearer <token>  (injected in lib/server/api.ts)
Spring  interceptor resolves token → userId → request scope → services scope all queries to it
```

The backend owns client secrets, code exchange, profile fetch, user creation, and
session issuing. The browser visiting the IdP consent page is inherent to any OAuth
(the user logging into Google/GitHub, not our client calling an API), so this stays
consistent with CLAUDE.md. SvelteKit is a relay + the cookie holder.

## Database — `V2__auth.sql` (new Flyway migration)

```sql
create table users (
    id         bigint generated by default as identity (start with 1000) primary key,
    email      text unique,                 -- verified primary email; may be null if a provider hides it
    name       text,
    avatar_url text,
    created_at timestamptz not null default now()
);

create table user_identities (
    id               bigint generated by default as identity primary key,
    user_id          bigint not null references users (id) on delete cascade,
    provider         text   not null check (provider in ('google', 'github')),
    provider_user_id text   not null,        -- the provider's stable subject id
    email            text,
    created_at       timestamptz not null default now(),
    unique (provider, provider_user_id)
);
create index idx_user_identities_user on user_identities (user_id);

create table sessions (
    token        text primary key,           -- opaque, cryptographically random
    user_id      bigint not null references users (id) on delete cascade,
    created_at   timestamptz not null default now(),
    expires_at   timestamptz not null,
    last_seen_at timestamptz not null default now()
);
create index idx_sessions_user on sessions (user_id);

-- Auth is real now: a user-less write should fail loud, not silently land on the
-- orphaned single-user data. Drop the implicit default; existing user_id=1 rows keep their value.
alter table user_progress      alter column user_id drop default;
alter table user_topic_comfort alter column user_id drop default;
alter table review_sessions    alter column user_id drop default;
```

No FK is added from the three per-user tables back to `users` (per the handoff: leave
the orphaned `user_id = 1` data untouched). New users get ids ≥ 1000, so no collision.

## Account resolution (on callback)

1. Look up `user_identities` by `(provider, provider_user_id)` → if found, that user.
2. Else, if the provider returns a **verified** email and a `users` row has it → link
   a new `user_identities` row to that user (cross-provider linking, one account per
   verified email).
3. Else create a new `users` row + its `user_identities` row.

`isNewUser = true` only in case 3 — drives the post-login redirect to `/onboarding`.

GitHub: the `/user` response often omits email; call `GET /user/emails` and take the
primary verified one. Scope `read:user user:email`. Google: scope `openid email
profile`; read the verified email + sub from the id_token / userinfo.

## Session model

- Token: 32+ bytes of secure random, base64url. Stored verbatim as the `sessions` PK.
- Lifetime: **30 days** absolute (`expires_at`). `last_seen_at` updated on use.
- Cookie (set by SvelteKit on the web origin): name `session`, `HttpOnly`,
  `SameSite=Lax`, `Path=/`, `Secure` in prod only (off for local http), `Max-Age` =
  session lifetime.
- `oauth_state` cookie: short-lived (~10 min), HttpOnly, SameSite=Lax, cleared on
  callback.

## Backend work (Kotlin / Spring, hand-rolled)

Package `dev.lctracker.backend`.

- **`web/AuthController.kt`** (new):
  - `GET  /auth/{provider}/start` → `{ authorizeUrl, state }`. Builds the provider
    authorize URL (client_id, `redirect_uri = {APP_WEB_ORIGIN}/auth/{provider}/callback`,
    scope, signed state). Stateless.
  - `POST /auth/{provider}/callback` body `{ code, state }` → re-verify state, exchange
    code, fetch profile, resolve/create user, create session → `{ token, expiresAt, isNewUser }`.
  - `POST /auth/logout` (Bearer) → delete the session row.
  - `GET  /auth/me` (Bearer) → `{ userId, email, name, avatarUrl }`; 401 if no/expired session.
- **`auth/OAuthClient.kt`** (new): Google + GitHub token exchange + profile fetch, built
  on the same `RestClient` builder pattern as `seed/LeetCodeClient`. Provider config
  (endpoints, scopes) lives here.
- **`auth/StateCodec.kt`** (new): HMAC-SHA256 sign/verify of `state` (provider, nonce,
  expiry) with `AUTH_SESSION_SECRET`.
- **`auth/SessionService.kt`** (new): create / resolve / delete sessions; user
  upsert + identity linking.
- **`security/`** (new): a `HandlerInterceptor` (or `OncePerRequestFilter`) that reads
  `Authorization: Bearer`, resolves the session → `userId`, stores it as a request
  attribute, and **401s `/api/**`** when missing/expired. Exempt `/auth/**` and
  `/health`. A `@CurrentUserId` `HandlerMethodArgumentResolver` injects `userId: Long`
  into controller methods.
- **Thread `userId`:** every `/api` controller method gains a `userId` param; the five
  services (`CatalogService`, `ProgressService`, `OnboardingService`, `StatsService`,
  `OffScriptService`) take `userId` instead of the `DEFAULT_USER_ID` constant. Entities
  already carry `var userId`; set it on construction (`UserProgress`, `ReviewSession`,
  `UserTopicComfort`). `DEFAULT_USER_ID` is removed.
- **New repos:** `UserRepository`, `UserIdentityRepository`, `SessionRepository`, +
  matching JPA entities `User`, `UserIdentity`, `AuthSession`.
- **Config:** read `GOOGLE_*`, `GITHUB_*`, `AUTH_SESSION_SECRET`, `APP_WEB_ORIGIN` via
  `@ConfigurationProperties`; surface in `application.yml`.

## Web work (SvelteKit)

- **`routes/signin/+page.server.ts`:** `google`/`github` actions → call backend
  `/auth/{provider}/start`, set the `oauth_state` cookie, 303-redirect the browser to
  `authorizeUrl`. **Remove the `guest` action.**
- **`routes/signin/+page.svelte`:** remove the guest button, the OR divider, and the
  guest note (keep the legal line).
- **`routes/auth/[provider]/callback/+server.ts`** (new): verify `state` vs cookie,
  relay `{ code, state }` to backend, set the `session` cookie, clear `oauth_state`,
  303 to `/onboarding` (new) or `/` (returning). Render a friendly error on failure.
- **`routes/auth/logout/+page.server.ts`** (new): action → backend `/auth/logout`,
  clear the `session` cookie, 303 to `/signin`.
- **`lib/server/session.ts`:** replace the hardcoded `{ userId: 1 }`. `getSession`
  reads the `session` cookie; the token is what gets forwarded. (Identity details come
  from `/auth/me` when needed.)
- **`lib/server/api.ts`:** inject `Authorization: Bearer <token>` from the request's
  session on every backend call — the one seam. Map backend **401** to a typed signal.
- **`hooks.server.ts`:** populate `locals.session` from the cookie (token presence).
- **`routes/+layout.server.ts`:** the gate keys on a **valid** session — validate via
  `/auth/me`; on 401, clear the cookie and redirect to `/signin`. Keep the
  onboarding-cookie second stage. (Replaces the old `signedIn`/`authMethod` cookies.)
- **`app.d.ts`:** update the `Session`/`Locals` shape.
- **`ProgressStrip.svelte`:** the dimmed gear becomes an active "Sign out" control that
  POSTs to `/auth/logout`. Marked temporary (Settings is still out of scope).

## Config / secrets

Backend (`.env.example` placeholders; real values in `.env`, Render dashboard, and
`docker-compose.yml` backend env):

```
GOOGLE_CLIENT_ID=
GOOGLE_CLIENT_SECRET=
GITHUB_CLIENT_ID=
GITHUB_CLIENT_SECRET=
AUTH_SESSION_SECRET=          # HMAC key for state + session token signing
APP_WEB_ORIGIN=http://localhost:5173   # used to build redirect_uri; allow-listed
```

`render.yaml`: add the same keys as `sync:false` env vars. Web needs no new secrets.

Provider registration (manual, by the repo owner — see verification caveat):
- Google Cloud Console → OAuth consent + credentials; redirect URI
  `{APP_WEB_ORIGIN}/auth/google/callback` (dev: `http://localhost:5173/auth/google/callback`).
- GitHub → Developer settings → OAuth Apps; callback
  `{APP_WEB_ORIGIN}/auth/github/callback`.

## Security considerations

- `state` is HMAC-signed (origin/CSRF) **and** echoed against the `oauth_state` cookie
  (binds the callback to the browser that started it).
- Session token is opaque + server-side → logout/expiry revoke immediately.
- Cookies `HttpOnly` + `SameSite=Lax`; `Secure` in prod.
- Backend 401s any `/api/**` without a valid session — no silent fallthrough to a
  default user once `DEFAULT_USER_ID` is gone.
- `redirect_uri` is derived from the server-side `APP_WEB_ORIGIN`, never from request
  input, so it can't be redirected off-host.

## Verification — what's testable here vs. by the owner

- **Automated (this work):** state sign/verify, account-resolution logic (new / link /
  existing), session create/resolve/expire, the interceptor's 401 behavior, the
  `userId` threading (services scope to the passed id), and the SvelteKit relay/gate
  logic. Backend compiles + tests green; web type-checks + builds.
- **Owner-run (needs real OAuth apps + a browser):** the actual Google/GitHub consent
  click-through end to end. I cannot register the OAuth apps or hold their secrets. A
  registration + manual-test checklist ships with the work; the real click-through is
  explicitly **not** verified by me.

## Milestones (each independently testable)

1. **Schema + session plumbing.** `V2__auth.sql`, entities/repos, `SessionService`,
   the interceptor + `@CurrentUserId`, `userId` threaded through all services, `/auth/me`
   + `/auth/logout`. _Acceptance:_ `/api/**` 401s without a session; with a manually
   inserted session row, data is scoped to that user; backend tests green.
2. **Google end to end.** `OAuthClient` (Google), `/auth/google/*`, SvelteKit signin
   action + callback route + cookie + gate. _Acceptance (owner):_ click → Google consent
   → land logged in → `/auth/me` returns your email → onboarding saves under your id.
3. **GitHub end to end.** GitHub provider (incl. `/user/emails`) + cross-provider email
   linking. _Acceptance (owner):_ same flow; same email across providers → same account.
4. **Logout + 401 handling.** Gear "Sign out"; gate redirects to `/signin` on 401.
   _Acceptance:_ logout invalidates server-side; cleared session bounces to `/signin`.

iOS (ASWebAuthenticationSession → same endpoints, token in Keychain) is explicitly
**out of scope** for this work.

## Out of scope

Settings screen, push/reminders, iOS auth, account-management UI, PKCE, refresh tokens,
deeper analytics. Per CLAUDE.md MVP guardrails.
